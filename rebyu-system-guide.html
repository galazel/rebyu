00Defense day: the two 5.0 risks

Your rubric awards a failing 5.0 in exactly two technical situations: the system is not deployed, and the system does not run during the defense. Everything in this section exists to stop those happening.

The single biggest risk is the venue's internet.

Your database is PostgreSQL on Supabase and your sign-in is AWS Cognito. Both live in the cloud. If the venue has no working internet, the system cannot read data and nobody can log in — the containers will be running and the app will still be dead. Verify the connection the moment you arrive, and have a phone hotspot ready as a backup.

Run the pre-flight check when you arrive

There is a script in the repository that tests all fifteen things that have to be true. Run it from the project folder:

powershell -ExecutionPolicy Bypass -File defense-preflight.ps1

It checks, in order: internet and DNS, that Supabase is reachable, that all five containers are up, that the frontend, backend and AI service each respond, that the AI service can reach its database, that a real query returns data, and that both cold and warm reads are fast enough. Every line prints PASS or FAIL, and a FAIL tells you the fix.

What "normal" looks like, so you don't panic

That one-off spike is the Supabase connection pooler opening a fresh connection after idling. It is normal and it settles immediately. Click through your demo path once before the panel arrives — that warms both the connection pool and the Redis cache, and everything you then show the panel will be fast.

01The three services

REBYU is not one program. It is three services plus two infrastructure containers, wired together by docker-compose.yml at the repository root. This is the first thing to be able to draw on a whiteboard.

frontend

React + Vite, served by nginx. Port 3000 → 80. All UI, routing and state.

backend

Spring Boot (Java). Port 8080. The system of record — auth, business rules, all persistence.

python-api

FastAPI. Port 8000. AI generation, the tutor, and the BKT mastery engine.

redis

Port 6379. Response caching, so repeated reads don't hit the database.

rabbitmq

Ports 5672 / 15672. Message queue for background AI work.

The sentence that answers "how does it work?"

The React frontend talks only to Spring Boot. Spring Boot owns the database and all business rules, and calls the Python service over HTTP when it needs AI generation or a mastery calculation. The frontend never calls Python directly.

Knowing the direction of the arrows matters more than any single file. A panelist asking "how do the components connect?" wants exactly this: one inbound path, one internal hop, one database.

Why two backends?

Java handles transactions, security and relational data — things Spring is strong at. Python handles AI and statistics, because the LLM and ML ecosystem lives there. Splitting them means a slow AI generation job never blocks a learner loading their dashboard.

On the frontend, ProtectedRoute gates each route group:

<Route element={<ProtectedRoute allowedRoles={["ADMIN"]} />}>
    <Route path="/admin" element={<DashboardLayout />}>

On the backend, config/SecurityConfig.java declares which URL patterns require authentication, and auth/security/RoleGuard.java checks the role inside the service layer.

Identity comes from AWS Cognito. auth/service/CognitoAuthService.java and CognitoAdminService.java handle sign-in and account administration, and the users table carries a cognito_sub column linking each local row to its Cognito identity. Spring Boot is configured as an OAuth2 resource server, so it validates the bearer token on each request rather than issuing its own.

The critical point to make

Frontend route guards are only convenience — they stop a wrong menu appearing. Real security is server-side, because anyone can edit JavaScript in their browser. If a panelist asks whether hiding a button is enough, this is the answer they want.

08The algorithms

Your checklist names algorithms explicitly. REBYU has three working together, each answering a different question. Everything below is read from your actual source — file and line, not textbook theory.

BKT

Does this learner know this lesson? → a probability per lesson.

IRT

How able is this learner overall? → a single number, theta.

Selector

Given both, which question comes next?

BKT — Bayesian Knowledge Tracing

adaptive/engine/BktModel.java — only 33 lines, and you should be able to reproduce it.

Four parameters, each clamped to a safe range in your code:

ParamMeaningYour clamp
priorP(knew it already)0.01 – 0.99
learnP(learns it on this step)0.001 – 0.9
guessP(correct while not knowing)0.01 – 0.49
slipP(wrong while knowing)0.01 – 0.49

The update is two steps — evidence, then learning:

// Step 1: Bayes on what we just observed
if (correct)  posterior = p(1-slip) / [ p(1-slip) + (1-p)·guess ]
else          posterior = p·slip    / [ p·slip    + (1-p)(1-guess) ]

// Step 2: they may have just learned it
return posterior + (1 - posterior) · learn

That second line is the part most students forget in a defense. Bayes alone only revises belief about what was already true; the learning term accounts for the learner acquiring the skill during the exercise itself. Mastery can therefore rise even after a wrong answer.

Why guess and slip must be capped below 0.5

If guess could reach 0.5 or above, a correct answer would be weak or negative evidence of knowing, and the update would misbehave. Capping both at 0.49 keeps a correct answer always positive evidence. That is the reasoning behind the clamp, and it is a strong thing to volunteer.

IRT — a three-parameter logistic model

adaptive/engine/IrtModel.java. Each item has three parameters, not one:

ParamNameMeaningRange
adiscriminationHow sharply the item separates able from unable learners0.2 – 4.0
bdifficultyThe ability level where P(correct) is halfway up−4 – 4
cguessingFloor probability — a 4-option MCQ is never 00 – 0.5

The probability a learner of ability θ answers correctly:

P(θ) = c + (1 - c) · 1/(1 + e^(-a(θ - b)))

Your difficulty labels map onto the θ scale as EASY = -1.5, AVERAGE = 0.0, HARD = +1.5, and θ itself is clamped to [-3, +3].

How theta updates — the part that impresses

Your system does not just nudge θ up on a right answer. IrtModel.update() is a Bayesian update that also tracks how confident it is, as a standard error σ:

info     = a²·(q/p)·((p-c)/(1-c))²      // Fisher information
gradient = a·(u - p)·(p - c) / (p(1-c))  // u = 1 correct, 0 wrong
gain     = σ² / (1 + σ²·info)

θ_new = θ + gain · gradient
σ_new = sqrt( 1 / (1/σ² + info) )        // floor 0.75

Two consequences worth stating out loud:

  • Surprising answers move θ more. (u − p) is the surprise: if the model expected 0.9 and the learner got it wrong, the gradient is large.
  • Confidence grows, so later answers move θ less. σ shrinks with every item, which shrinks gain. Early answers matter most — exactly how a real adaptive test behaves.

θ is then reported to learners on a friendly scale via proficiencyRating:

rating = (θ + 3) / 6 × 100     →  ≥75 Advanced
                                  ≥50 Proficient
                                  ≥25 Developing
                                  else Novice

Item information — why "near θ" is optimal

Fisher information peaks when the item's difficulty sits near the learner's ability. An item far too easy or far too hard carries almost no information: you already knew the outcome. The selector maximizes information, which is the formal version of "ask something at their level".

The selector — how the two models combine

adaptive/engine/AdaptiveItemSelector.java, the select() method. It runs six stages:

1DedupeDrop served ids, identical stems, and near-duplicate stems by token overlap
2LevelKeep only items with |b − θ| within 0.75 of the closest item
3TierTake the best tier present and discard the rest entirely
4GroupBucket survivors by lesson and tier
5LessonScore each lesson, pick the highest
6ItemRank by information × type weight, sample from the top-K

The four tiers are a strict no-repeat ladder:

TIER_UNSEEN           ← never shown to this learner  (preferred)
TIER_NEW_THIS_CYCLE   ← seen before, new this cycle
TIER_SEEN_THIS_CYCLE  ← already seen this cycle
TIER_REPEAT           ← last resort

How a lesson is chosen

lessonScore = coverageDeficit
            + explorationWeight × uncertainty
            + small random noise

uncertainty = pKnown × (1 - pKnown)

That uncertainty term is the elegant bit, and it's where BKT feeds IRT. It is maximized at pKnown = 0.5 — exactly where the system is least sure whether the learner knows the lesson. A lesson at 0.95 or 0.05 is settled and scores near zero. So the engine naturally spends questions where they resolve the most doubt.

coverageDeficit is how far behind a lesson is versus its target share, which stops the exam fixating on one weak topic and ignoring the syllabus.

Weak-lesson focus

focusPlan() reserves a share of the paper (weakShare) for lessons below a mastery threshold, split in proportion to (1 − pKnown) so the weakest lesson gets the largest slice. It has a deliberate guard: if every lesson counts as weak it returns an empty plan and falls back to proportional coverage, because "focus on everything" is not focus.

Two touches that show care

Top-K sampling, not greedy. chooseItem sorts by information then picks randomly among the best topK. Always taking the single best item would make the exam deterministic and gameable, and would hammer the same few questions.

Type balancing. typeWeight compares each question type's share of the pool against its share of what's been served, and boosts under-served types by 1 + 3 × deficit. Without it, maximizing information alone would drift toward whichever type happens to discriminate best.

The nuance to volunteer unprompted

Not every assessment is adaptive. Quizzes and unit exams adapt; diagnostic and mock exams are fixed papers by design. A mock must mirror the real certification paper, and a diagnostic must touch every lesson once to establish a baseline — adapting it would defeat its purpose. AdaptivePolicy.isAdaptive(exam) is where that decision is made.

Readiness — "am I ready for the real exam?"

python-backend/app/services/readiness_service.py, 77 lines. A weighted average of eight signals:

mastery (average BKT across lessons)    diagnostic score
lesson quiz score                        middle exam score
major exam score                         mock exam score
lesson progress                          streak

normalized_weight = weight / total_weight
readiness        += score × normalized_weight

Weights are normalized rather than assumed to sum to 1, so you can retune any single READINESS_* value in .env without rebalancing the rest. The result maps to a level: ≥85 exam_ready, ≥70 nearly_ready, ≥50 developing, below that needs_review.

The response returns every component with its own score, weight and contribution — so the UI can show why a learner is at 62, not just the number.

One behaviour to be ready to defend.

A missing signal is scored 0.0, not excluded: effective = 0.0 if score is None else float(score). So a learner who has never sat a mock exam is pulled down by the mock component. That is arguably correct — you are not exam-ready if you have never taken a mock — but it is a choice, and the priority engine below makes the opposite choice. If a panelist spots that, the honest answer is that readiness treats absence as evidence and priority does not.

Priority — "what should I study next?"

python-backend/app/services/priority_service.py. Scored per lesson from up to five weighted components:

ComponentWeightIncluded when
Mastery weakness (1 − mastery) × 1000.45always
Incorrect rate0.20there is any evidence
Mock-exam weakness0.10last assessment was a mock
Diagnostic weakness0.10last assessment was the diagnostic
Review urgency (time since update)0.05there is a timestamp

Unlike readiness, this divides by the weight of the components actually present (weight_total = sum(weight for _, weight in components)), so a lesson is never penalized for lacking a mock-exam score. The score then classifies into CRITICAL / HIGH / MEDIUM / LOW / ON_TRACK / STRONG, and anything below priority_min_evidence is tagged NEEDS_REASSESSMENT instead of being guessed at.

The reported-mastery guard — your best engineering story

reportable_mastery() in the same file. This is the most defensible piece of judgment in the codebase, and it comes with a real incident behind it.

BKT's P(L) answers "what is the chance they know this now", and it is recency-weighted by design — a run of correct answers is supposed to move it sharply. With untrained fallback parameters, that produced a genuine absurdity: a learner who had answered 19 right and 70 wrong on a lesson reached 0.98 mastery after three correct answers.

if evidence < 10:            # not enough to judge
    return mastery           # leave the model alone

accuracy = correct / evidence
return min(mastery, accuracy + 0.35)   # cap what we *claim*

Three things make this a good answer rather than a hack, and all three are worth saying:

  • It caps the reported value, never the stored one. The stored probability feeds the next update as mastery_before; capping it would push a doctored prior into the chain and compound at every step. The model stays the model.
  • The 0.35 headroom is deliberate. A learner who has genuinely improved should read above their lifetime average, because that average still carries everything they have since learned. What they cannot do is read as mastered on the strength of three answers.
  • It is temporary by design. It guards against untrained parameters; once per-lesson parameters are fitted from a real cohort it should rarely bind.

Cold start — why the parameters are hand-set

python-backend/app/ml/smart_defaults.py. A BKT fit needs many learners per skill before its parameters mean anything. With a handful, expectation-maximization finds parameters that explain those few learners' streaks and nothing else.

So every lesson starts from literature-range parameters — Corbett & Anderson's prior and learn rates, and the guess < 0.30, slip < 0.10 bounds from Baker et al. — varied only by what is known in advance: the item's difficulty sets guess and slip, the assessment type sets learn.

pyBKT is still present as the reference implementation: build_model assembles its transition matrix and emissions from these numbers so Model.predict runs the standard forward pass, and evaluate scores those predictions against the real response log. But there is no fit call anywhere. The live per-answer update runs in plain Python so one event costs one row rather than loading a model.

If you are asked "why didn't you train the model?"

Because training on too few learners is worse than not training. The parameters would overfit a handful of streaks and look rigorous while meaning nothing. The system instead uses published parameter ranges, keeps pyBKT as the reference implementation to validate against, and is built so that fitted per-lesson parameters can replace the defaults once there is a cohort to fit them from.

09End-to-end data flow

If you can narrate one request end to end, you can answer most "how does it work" questions. Here is a learner answering a question.

1ReactLearner clicks an answer; the component calls a function in services/
2ReactHTTP POST to Spring Boot with the JWT in the Authorization header
3SpringSecurityConfig validates the token and identifies the user
4SpringController receives the DTO and calls the service layer
5SpringService grades the answer and applies the business rules
6PostgresRepository saves the response and updates the attempt
7SpringA mastery event is written to the BKT outbox table
8SpringA dispatcher posts it to Python: POST /mastery/events/batch
9FastAPIBKT recalculates mastery probability for that lesson
10SpringAdaptive selector uses the updated state to pick the next question
11ReactResponse returns; the UI renders the next question

Why an outbox, and not a direct call?

This is the single best detail to volunteer, because it shows engineering judgment rather than memorization.

If Spring called Python directly while saving the answer and Python were down, the learner's answer could be lost or the request would hang. Instead the event is written to a database table in the same transaction as the answer. A separate dispatcher reads that table and forwards it.

So the learner's answer is never at risk from an AI-service outage; the mastery update simply catches up afterwards. That is the transactional outbox pattern.

10Likely panel questions

Open each one and say the answer out loud. Speaking it is what makes it stick.

Walk us through your system architecture.

Three services in Docker: a React frontend on 3000, a Spring Boot backend on 8080, and a FastAPI AI service on 8000, plus Redis for caching and RabbitMQ for background jobs. The frontend talks only to Spring Boot. Spring Boot owns the PostgreSQL database and all business rules, and calls the Python service over HTTP for AI generation and mastery calculations.

Why did you use two different backend languages?

Separation of concerns. Spring Boot gives us mature transaction management, security and ORM for relational data. The AI and machine-learning ecosystem — LangGraph, the model clients, the BKT implementation — lives in Python. Splitting them also means a slow AI generation job never blocks a learner loading their dashboard.

Where is your database schema defined?

In the 115 JPA entity classes under the Java source tree. Each @Entity is a table, its fields are columns, and its relationship annotations define the foreign keys. Hibernate derives the schema from those classes. We run PostgreSQL on Supabase.

What algorithm personalizes the learning?

Two. Bayesian Knowledge Tracing estimates the probability a learner has mastered each lesson, updating on every answer and accounting for guessing and slipping. Item Response Theory models learner ability as theta and picks the question most informative at that ability. Quizzes and unit exams adapt; diagnostics and mock exams are fixed papers on purpose.

How do you secure the application?

Identity is handled by AWS Cognito. Spring Boot runs as an OAuth2 resource server, so every request carries a bearer token that config/SecurityConfig.java validates, and each row in users links to its Cognito identity through cognito_sub. There are four roles — ADMIN, LEARNER, INSTITUTION, DEPARTMENT_HEAD. The frontend uses ProtectedRoute to hide screens, but that is only convenience. The real enforcement is server-side in SecurityConfig and RoleGuard, because browser code can be modified by the user.

What happens if the AI service goes down?

Core learning keeps working. Mastery events are written to an outbox table in the same transaction as the learner's answer, and a separate dispatcher forwards them. If Python is unavailable the events stay queued and are delivered when it recovers. Answers are never lost and the learner is never blocked.

How is the frontend organized?

By role and by feature. pages/ has one file per screen grouped into admin, learner, institution and public. components/ holds reusable UI, services/ holds every API call, hooks/ holds reusable stateful logic. There are three layouts, one per audience, and routes are lazy-loaded so each role only downloads its own code.

How do you know the system works?

There are 225 frontend test files covering the numbered test cases, run with Vitest, plus JUnit tests on the Java side. The build runs a TypeScript typecheck and a production Vite build. Say the real number and offer to run them — a live green suite during a defense is persuasive.

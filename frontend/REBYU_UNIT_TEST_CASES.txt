PURPOSE AND SCOPE
This is a repository-informed baseline for the identified frontend, Java service
and Python logic units. It includes success, invalid input, boundaries, ownership,
duplicate requests, failure handling and recovery. It is not a claim that every
possible input or branch is covered. Expand data-driven cases for each supported
question type, account role, certification, diagram format and activity schema.

This catalog supersedes the earlier chat's sample numbering. TC identifiers here
are local to this file; they do not map to docs/TC-001_to_TC-010_Test_Cases.txt.

Only this document was created, inside frontend/, in accordance with AGENTS.md.
Backend code was read to plan tests; it was not changed. Backend implementations
and test changes remain outside the authorized frontend editing boundary.

WHAT NEEDS UNIT TESTING
P1: Access control, authentication state, attempt ownership, grading, duplicate
submission, payment verification, entitlements, reward accounting, mastery math,
institution isolation, AI error handling and generation recovery.
P2: Date/time formatting, exports, notifications, file-preview cleanup, dashboard
state and administrative component interactions.

Each case tests ONE function, service or component with collaborators mocked.
Rows naming both frontend and backend describe a unit at the applicable layer:
choose the named component OR service, not a live end-to-end chain.
For a row with multiple independent inputs, run one assertion set per input.
Use the source's configured thresholds, schemas and scoring rules rather than
inventing product requirements. A requirement that is ambiguous should be
clarified before marking that case Passed.

TEST SETUP
Frontend: mock API modules, auth session, navigation, local storage, browser file
APIs and speech/media providers as needed. Use fake timers for countdowns,
Pomodoro and streaming coordination. Restore mocks and storage between tests.
Java: instantiate the service with mocked repositories, payment verifier, AI
client, Judge0 client and reward/event collaborators. Verify returned values,
exceptions and collaborator calls. Repository mocks cannot prove DB rollback.
Python: use deterministic fixtures and monkeypatch AI, vector retrieval, messaging,
storage and time dependencies. No paid model calls or production writes.
Use synthetic learners and organizations. Freeze random sources for sampling
tests and time for date-sensitive tests. Never place real credentials in tests.

HOW TO RECORD RESULTS
1. Arrange the stated inputs and mocks.
2. Invoke the target function, service method or component action.
3. Assert the exact result, state change, exception or collaborator interaction.
4. Replace Action Result with the actual observed behavior.
5. Enter the actual test date using MM/DD/YY.
6. Set Result to Passed, Failed or Blocked. Attach failure evidence in Action Result.
For a grouped case, mark Passed only when every specified input passes.

03How the schema is organized

Two Postgres schemas, owned by two different services. This is the single most important structural fact about your database.

public — 113 tables

Owned by Spring Boot. Defined by JPA entity classes. All business data: users, curriculum, questions, attempts, institutions, billing.

bkt — 9 tables

Owned by the Python service. Defined by SQLAlchemy models. Mastery state, priority scores, and AI workflow tracking.

The separation is deliberate: each service owns its own tables and neither writes into the other's. They exchange data over HTTP, not by sharing a table. When a panelist asks how you avoided coupling two backends to one database, this is the answer.

There is no migration tool in play.

On the Java side the entity classes are the schema — Hibernate derives the tables from them. So "where is your schema defined?" has a precise answer: the 113 @Entity classes. Python manages its own bkt schema separately through SQLAlchemy.

04The curriculum tree

Four levels, each a table, each pointing at its parent. Everything else in the system hangs off this spine.

certifications          "IT Passport"
  └─ major_categories     "Technology"        certification_id →
       └─ middle_categories  "Basic Theory"   major_category_id →
            └─ lessons         "Binary"       middle_category_id →
                 └─ questions                 lesson_id →
                      └─ choices              question_id →

Each arrow is a @ManyToOne with a NOT NULL foreign key, so no lesson can exist without a parent category and no question without a lesson. That is why the lesson is the unit of mastery: it is the lowest level that owns questions, so it is the natural thing for BKT to track.

Note that questions.parent_question_id points back at questions — a self-reference that supports item sets, where several questions share one stimulus.

05The assessment chain

Five tables turn "a learner sits an exam" into stored data. Being able to name them in order is worth rehearsing.

exams                       the definition — what can be sat
  exam_questions            which questions are in it, order, points
assessment_attempts         one learner's run: status, timing, pauses
  assessment_attempt_questions   the question actually served
    assessment_attempt_answers   what the learner submitted
exam_results                the final scored outcome
Why served questions are stored separately

In an adaptive exam the questions are chosen during the attempt, so they cannot come from exam_questions alone. assessment_attempt_questions records what this learner actually saw, in the order they saw it. It is also what makes an attempt reproducible afterwards for review.

06Data flows

Flow A — A learner answers one question

1ReactPOST the answer with the JWT
2SecurityConfigValidate token, resolve the user
3ControllerReceive DTO, call the service
4ServiceGrade it against the stored answer
5attempt_answersINSERT the submission
6learner_skill_statesUPDATE theta and standard error (IRT)
7bkt_event_outboxINSERT a mastery event — same transaction
8COMMITAnswer and event become durable together
9DispatcherLater: POST the event to Python
10learner_lesson_masteryUPSERT the new probability
11bkt_mastery_eventsINSERT the audit row with before/after
12SelectorPick the next question from the updated state

Step 7 is the one to highlight. The event is written to a table in the same database transaction as the answer. If the commit succeeds, both exist; if it fails, neither does. The dispatcher then delivers it separately. That is the transactional outbox pattern, and it is why an AI-service outage can never lose a learner's answer.

Flow B — Why there are three mastery tables

TableShapeAnswers
learner_lesson_masteryOne row per learner+lessonWhat do they know now?
learner_lesson_mastery_historyAppend-onlyHow did it change over time?
bkt_mastery_eventsAppend-onlyWhat evidence caused each change?

The current-state table is small and fast to read on every page load. The history tables are never read in the hot path but let you prove how a score was reached. bkt_mastery_events even stores parameters_used as JSON, so a past calculation can be reproduced after the parameters change.

Flow C — Idempotency, so a retry cannot double-count

If the dispatcher retries after a timeout, the same event could arrive twice and mastery would be updated twice from one answer. Two guards prevent it:

  • bkt_mastery_events.source_event_id is UNIQUE — a duplicate insert simply fails.
  • bkt_processed_events stores a payload_hash alongside the id, so the same id arriving with different content is detected and flagged rather than silently reprocessed.

Flow D — AI generation, which is asynchronous

1generation_requestsAdmin request stored as PENDING
2RabbitMQJob queued
3workflow_runsPython records the run and its stage
4workflow_eventsEach step appended with a monotonic seq
5WebSocketBrowser streams progress; reconnect replays from last_seq
6generated_question_draftsApproved output lands here
7questionsAdmin accepts; rows written to the real bank

Generation can take minutes, so it cannot be a blocking HTTP call. workflow_events.seq is unique per run, which is what lets a dropped browser connection resume exactly where it left off instead of losing the timeline.
